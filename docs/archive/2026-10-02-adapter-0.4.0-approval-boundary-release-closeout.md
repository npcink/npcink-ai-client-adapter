# Adapter 0.4.0 Approval Boundary Release Closeout

Date: 2026-10-02
Status: released

## Scope

This closeout records the 0.4.0 release: restricting the unified
`approve-and-execute` action to WordPress administrator sessions, aligning
every contract document with that boundary, shipping the governed MCP tool
surface without a self-approval tool, and the release process lessons
learned along the way.

The release keeps Adapter inside its thin channel boundary:

- reads still route through WordPress Abilities API;
- governed writes still route through Governance Core proposal and
  commit-preflight truth;
- final writes still require explicit Adapter execution profiles after Core
  approval;
- the unified approve-and-execute action remains available, but only from a
  WordPress administrator session — signed AI clients never hold approval
  authority.

## The Problem

The pre-release boundary audit compared the published security claims with
the actual server-side enforcement chain:

- `threat-model.md` said the AI client "must never hold final-write
  authority" and that the gate stops prompt-injection-steered actions through
  "proposal, **human approval**, commit-preflight, and allowlisted
  execution".
- In reality, `/proposals/{id}/approve-and-execute` was reachable by any
  paired key holding `npcink.execute` (requested by default at pairing), and
  for a pending proposal the Adapter itself called Core's approve endpoint
  with its app token before executing with `commit=true`.
- MCP tool `approve_and_execute` exposed that path to the model directly;
  the only gates were the model-supplied `intent` argument and tool
  description wording.

A prompt-injected model with a default-paired key could therefore propose,
approve, and execute a final write in one call. The "human approval" gate was
not human for enforced (signed-key) clients.

## The Decision

Option A was chosen: keep the unified action, reserve it for WordPress
administrator sessions (cookie, Application Password, or basic auth as a
`manage_options` user). Rationale:

- it matches every existing published promise ("user-triggered",
  "a WordPress administrator must approve it in the Core admin", the threat
  model, and the positioning line "the Npcink channel gives it your
  approval");
- the change is small and reviewable (permission surface, not protocol);
- Application Password clients remain admin-equivalent by design — that is
  the documented conventional boundary class, honestly disclosed through
  `client_policy.boundary_enforcement`.

The rejected alternative (a dedicated `npcink.approve` key scope) would have
kept a delegated-approval mode but required rewriting the security narrative;
it can still be introduced later as an explicit, separately-approved scope if
product demand appears.

## Enforcement Layers

Three independent fail-closed layers were added:

1. Route permission: `can_use_unified_approve_and_execute` returns
   `npcink_openclaw_adapter_approve_requires_admin_session` (403) with
   `operator_feedback` describing the two-step migration path.
2. Key-scope gate: `client_key_scope_allows_request` hard-denies the route
   before any scope check, and the route was removed from
   `client_key_route_requires_execute_scope` so no future scope grants it.
3. Handler re-check: the route refuses `current_signed_authenticated`
   requests even if a future refactor bypasses the first two layers.

Contract surfaces were updated in the same change so clients can discover
the boundary: `client_policy.write_flow.admin_session_only_routes` and
`signed_client_self_approval=forbidden`, health/help
`admin_session_only_execution_routes` / `signed_client_execution_routes`,
and the `unified_approve_and_execute` guidance block with
`authorization=wordpress_admin_session_only`.

The signed-client governed path is now two-step: create the proposal, wait
for a human to approve it in the Core admin, then call
`POST /proposals/{proposal_id}/execute` with `--intent=commit`. The Core
preflight signed-client fingerprint binding already required the same client
to propose and execute, so no Core changes were needed.

## MCP Surface Decision

`@npcink/openclaw-adapter-cli` 0.5.0 deliberately has no
`approve_and_execute` tool. The MCP tool table is itself a boundary: whatever
tool the model can call, it can be prompt-injected into calling. Execution
exposure is limited to `commit_preflight` (intent-gated, executes nothing)
and `execute_approved` (intent-gated, final write, only for proposals a
human already approved in the Core admin). The positioning notes roadmap row
now records this as a decision, not an omission.

## Lessons And Norms

1. **Audit promises against enforcement, not docs against docs.** The P0 gap
   was found by walking the actual server-side chain (route permission →
   scope gate → upstream dispatch) against each published security claim.
   Doc-to-doc review would have passed; the claims were internally
   consistent but the code disagreed with all of them.
2. **The MCP tool table is a permission surface.** Exposing a capability to
   the model is granting it. Intent arguments and tool descriptions are
   prompt-level guidance, not enforcement; anything that must never happen
   must be absent from the tool table and blocked server-side.
3. **Version pins are re-install surfaces.** After removing a capability
   from a published package, every install command, admin UI copy string,
   and doc example that pins an older version will reinstall it. Grep the
   whole repo for the old version string when cutting a security-relevant
   CLI/plugin pair, and keep the companion assertions in `tests/run.php`
   pointing at the new pin.
4. **Route-response contract changes must ripple into acceptance assertions
   the same day.** The execute route never had a top-level `success` field
   (an approve-and-execute extra); the fixture script inherited the stale
   assertion and only the first live run caught it. When changing which
   route an acceptance script exercises, re-derive the assertions from the
   route's actual payload builder.
5. **A git tag is not a WordPress.org release.** 0.3.3 had a git tag, a
   changelog entry, and a readme stable tag, but no SVN commit — WordPress.org
   shipped 0.3.2 until this release. Before any wp.org upload, check
   `svn ls .../tags` and the trunk `Version:` header; the release gate doc
   now carries this check.
6. **Squash-merge makes `git branch --merged` useless for cleanup.** Verify
   merged topic branches by tree-diffing the branch tip against its squash
   commit (`git diff <branch> <squash-sha> --stat` is empty), then delete
   both sides.
